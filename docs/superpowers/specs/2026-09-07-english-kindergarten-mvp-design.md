# PREPPY 영어유치원 DB MVP 설계

- 상태: Owner 화면·구조 승인 반영
- 설계일: 2026-09-07
- 대상: 서울 강남구·서초구에서 수집한 영어유치원 25곳
- 후속 단계: 구현 계획 작성 후 스키마·반입·UI 구현

## 1. 목표

보호자가 영어유치원을 알아볼 때 가장 먼저 묻는 원비, 입학설명회, 운영 연령, 커리큘럼, 셔틀, 급식과 후기를 기관별로 빠르게 비교할 수 있게 한다. 공식 자료에서 확인한 사실, 외부 후기에서 요약한 의견, 아직 확인하지 못한 정보를 섞지 않는다.

초기 25곳은 프로덕션 DB에 `DRAFT`로 반입한다. 기관 공개 기준을 통과한 곳만 별도 승인 절차를 거쳐 `PUBLISHED`로 전환한다. 원비나 셔틀처럼 나중에 확보되는 정보는 기관 전체를 다시 반입하지 않고 항목별로 추가하거나 새 버전으로 교체할 수 있어야 한다.

## 2. 확정된 제품 결정

1. 25곳을 각각 독립적인 `institution`으로 관리한다.
2. 브랜드와 캠퍼스의 상하 관계를 추가하지 않는다.
3. 기존 사립초의 기관·출처·증거·일정 구조를 재사용하는 하이브리드 방식을 사용한다.
4. 목록 화면은 비교 중심 A안을 사용한다.
5. 상세 화면은 핵심 답변을 먼저 보여주고, 세부 정보와 근거를 같은 페이지에서 확인하는 단일 스크롤 구조를 사용한다.
6. 항목이 비어 있다는 이유로 정보가 없다고 단정하지 않는다. 조사 전, 공식 안내에서 미발견, 접근 실패, 검수 필요를 구분한다.
7. 외부 후기는 공식 사실과 분리하고, 원문을 복제하지 않는다.

## 3. 사용자 과업과 정보 우선순위

주요 사용자는 다음 질문에 답을 얻으려는 보호자다.

1. 월 원비와 별도 비용은 얼마인가요?
2. 다음 입학설명회는 언제이고 어떻게 신청하나요?
3. 몇 세부터 다닐 수 있나요?
4. 영어 수업과 특별 활동은 어떻게 구성되나요?
5. 셔틀은 어느 지역을 다니고 비용은 얼마인가요?
6. 급식은 어떻게 제공되고 별도 비용이 있나요?
7. 공개 후기에서는 어떤 경험이 반복해서 언급되나요?
8. 이 정보는 어느 학년도 기준이고 어디에서 확인했나요?

목록에서는 원비, 운영 연령, 셔틀, 다음 설명회를 우선 노출한다. 상세에서는 이 네 항목을 요약한 뒤 원비, 설명회, 연령·커리큘럼, 셔틀, 급식, 후기 요약, 공식 출처 순서로 제공한다.

## 4. 정보 구조와 화면

### 4.1 영어유치원 목록

목록 상단에는 기관명·지역 검색과 핵심 필터를 둔다. 초기 필터는 지역, 원비 확인 여부와 범위, 운영 연령, 셔틀 운영 여부, 예정된 설명회로 제한한다. 데이터가 적은 초기 MVP에서 효용이 낮은 복합 필터나 지도 탐색은 추가하지 않는다.

각 기관 카드는 다음 정보를 제공한다.

- 기관명과 주소 요약
- 월 원비 또는 원비 확인 상태
- 운영 연령
- 셔틀 운영 상태
- 가장 가까운 설명회와 신청 상태
- 공식 정보 확인 여부와 내용 확인 날짜

기본 정렬은 `정보 많은 순`이 아니라 사용자 판단에 영향을 덜 주는 안정적인 정렬을 사용한다. MVP 기본값은 기관명 가나다순이며 사용자가 `설명회 가까운 순`, `원비 낮은 순`을 명시적으로 선택할 수 있다. 금액 기준과 적용 학년도가 다른 원비는 같은 수치처럼 정렬하지 않는다.

### 4.2 기관 상세

상단에는 기관명, 지역, 공식 운영 정보 확인 상태, 마지막 내용 확인 날짜를 표시한다. 지도, 전화, 공식 홈페이지 버튼은 실제 목적지와 행동이 준비된 경우에만 노출한다.

핵심 요약은 다음 네 칸으로 구성한다.

- 월 원비: 금액, 납부 기준, 적용 학년도, 별도 비용 여부
- 운영 연령: 최소 연령과 운영 반
- 셔틀: 운영 여부, 공개된 운행 범위, 비용 확인 상태
- 다음 설명회: 실제 날짜, 신청 상태, 신청 마감

본문은 앵커 메뉴를 제공하는 단일 스크롤 화면이다. 각 섹션은 확인된 값과 해당 값의 적용 시점·공식 출처를 함께 보여준다. 출처는 페이지 끝에만 모으지 않고 관련 정보 가까이에도 연결한다.

후기 요약에는 `공개 후기 요약 · 공식 정보 아님`을 명시한다. 반복 주제, 검토 대상 기간, 검토한 후기 수와 출처 링크를 제공하며 개인의 단일 주장을 기관의 사실처럼 표현하지 않는다.

### 4.3 반응형 원칙

모바일에서는 네 칸 요약을 두 칸 또는 한 칸으로 재배치하고 앵커 메뉴는 가로 스크롤을 허용한다. 표는 핵심 라벨과 값이 줄 단위로 쌓이게 하며, 날짜·금액·학년도가 서로 떨어져 의미가 달라지지 않게 한다. 외부 이동 버튼의 접근성 이름은 `기관 공식 홈페이지 열기`, `기관에 전화하기`, `지도에서 위치 보기`처럼 실제 동작을 설명한다.

## 5. 백엔드 아키텍처

### 5.1 재사용하는 공통 구조

- `institutions`: 기관 식별자, 이름, 주소, 연락처, 카테고리, 운영·공개 상태
- `sources`와 source binding: 공식 홈페이지, 공지, 공식 문서, 공식 SNS, 제3자 후기 출처
- `snapshots`와 `observations`: 수집 시점의 제한된 원문 근거와 해시
- `institution_facts`, `institution_fact_versions`, `institution_fact_version_evidence`: 기관의 현재 공식 사실과 버전·근거
- `opportunities`, opportunity version/evidence/binding: 설명회, 모집, 상담, 레벨 테스트와 신청 일정

공개 화면은 현재 상태이면서 검수된 사실 버전만 사용한다. `DRAFT` 기관은 공개 쿼리에서 제외한다.

### 5.2 사실 유형과 구조화 값

기존 사실 유형 중 `TUITION`, `TARGET_AGE_GRADE`, `CURRICULUM`, `TRANSPORT`, `ADMISSION_PROCESS`, `OPERATING_INFO`를 재사용하고 `MEALS`를 추가한다. `value_json`은 사실 유형별 런타임 스키마로 검증하며 자유 형식 객체를 그대로 통과시키지 않는다.

#### 원비

- 적용 학년도 또는 적용 기간
- 납부 단위: 월, 분기, 학기, 연간, 1회
- 기본 금액의 최솟값·최댓값과 통화
- 반 또는 프로그램별 금액
- 등록비, 교재비, 재료비, 급식비, 셔틀비 등 별도 비용
- 포함 항목
- 환불·변경 조건
- 기관에 추가 확인할 내용

#### 운영 연령

- 최소·최대 연령
- 기관이 사용하는 한국 나이·만 나이 기준
- 반 이름과 대상 연령
- 기준 학년도
- 중도 입학 가능 여부가 공식적으로 안내된 경우의 조건

#### 커리큘럼

- 수업 언어와 사용 비중이 공식적으로 제시된 경우의 값
- 읽기, 쓰기, 말하기, 프로젝트, 놀이 등 프로그램 구성
- 특별 활동
- 일과표 또는 운영 시간
- 반별 차이와 별도 프로그램

#### 셔틀

- 운영 여부
- 공개된 운행 지역과 노선
- 노선별 또는 월별 비용
- 등원·하원 구분
- 좌석이나 주소에 따른 이용 제한
- 상세 노선·비용의 별도 문의 필요 여부

#### 급식

- 급식과 간식 제공 여부
- 자체 조리, 위탁, 도시락 등 제공 방식
- 원비 포함 여부와 별도 비용
- 공개 메뉴 또는 식단 링크
- 알레르기 대응이 공식적으로 안내된 경우의 내용

구조화 값은 비교·필터용이고 `display_text`는 사용자에게 보여주는 검수된 설명이다. 화면에서 구조화 값만 조합해 공식 조건이나 예외를 탈락시키지 않는다.

### 5.3 항목별 조사 상태

`institution_section_coverage`를 추가한다. 기관과 섹션 조합은 하나의 현재 상태를 가진다.

- 섹션: 원비, 설명회, 운영 연령, 커리큘럼, 셔틀, 급식, 후기, 운영 정보
- 상태: `NOT_RESEARCHED`, `CONFIRMED`, `CHECKED_NOT_FOUND`, `ACCESS_FAILED`, `NEEDS_REVIEW`
- 마지막 조사 시각
- 조사 대상 학년도 또는 기간
- 확인한 source·snapshot 참조
- 내부 메모와 공개 가능한 안내 문구의 분리

`CONFIRMED`는 공개 가능한 현재 사실 또는 일정 근거가 있을 때만 사용할 수 있다. `CHECKED_NOT_FOUND`는 확인한 공식 안내의 범위와 시점이 기록된 경우에만 사용할 수 있다. 접근 실패를 미발견으로 변환하지 않는다. 최신 수집 실패 시에도 아직 유효한 이전 검수 정보를 자동으로 삭제하지 않는다.

### 5.4 후기 인사이트

`institution_review_insights`와 근거 연결을 추가한다. 후기 인사이트는 공식 사실 테이블에 저장하지 않는다.

- 대상 기관
- 수집 대상 기간
- 검토한 후기 수
- 반복 주제 목록
- 각 주제의 중립적 요약
- 출처 URL
- 수집·검수 시각
- 검수 상태와 현재 버전 여부

실명, 연락처 등 불필요한 개인정보와 장문의 원문은 저장하지 않는다. 표본이 적거나 출처 접근이 제한된 경우 그 한계를 함께 표시한다. 긍정·부정 점수나 기관 순위는 초기 MVP에 포함하지 않는다.

### 5.5 일정 모델

입학설명회는 `INFORMATION_SESSION`, 상담은 `CONSULTATION`, 모집은 `RECRUITMENT`, 레벨 테스트는 `LEVEL_TEST`로 저장한다. 행사 날짜, 신청 기간, 행사 상태를 서로 다른 필드로 관리한다. 설명회 신청 마감과 행사 종료를 같은 상태로 처리하지 않는다.

한 기관에 여러 설명회가 있으면 별도 opportunity로 보존한다. 공통 조건은 한 번 표시할 수 있지만 회차별 날짜, 시간, 장소, 대상과 신청 마감은 각 일정에 남긴다.

## 6. 읽기 모델과 데이터 흐름

영어유치원 화면은 공통 테이블을 직접 조립하지 않고 전용 공개 읽기 서비스가 반환하는 DTO를 사용한다.

### 목록 DTO

- 기관 식별자, 이름, 주소 요약
- 원비 비교값과 적용 학년도
- 최소·최대 운영 연령
- 셔틀 상태
- 다음 설명회와 신청 상태
- 항목별 coverage 상태
- 내용 확인 날짜

### 상세 DTO

- 기관 기본 정보와 외부 행동 링크
- 네 가지 핵심 요약
- 유형별 현재 사실과 표시 문구
- 예정·최근 설명회
- 후기 인사이트
- 각 항목의 공식 출처, 자료 수집 시각, 내용 확인 시각
- 공개용 빈 상태와 오류 상태

흐름은 다음과 같다.

1. 로컬 수집 산출물에 기관·사실·일정·출처·증거를 저장한다.
2. JSON 스키마, 참조 무결성, 중복, 체크섬을 검증한다.
3. 프로덕션 반입 전 read-only dry run으로 생성·갱신·거절 대상을 보고한다.
4. 승인된 스냅샷을 하나의 트랜잭션으로 반입한다.
5. 25개 기관은 `DRAFT`로 생성하고 검수된 사실 버전만 현재값으로 설정한다.
6. 공개 기준을 충족한 기관만 명시적인 publish 작업으로 전환한다.
7. 공개 API가 카테고리와 공개 상태를 제한해 목록·상세 DTO를 생성한다.

반입은 기관별 안정적인 외부 키와 스냅샷 체크섬을 사용해 멱등성을 보장한다. 같은 스냅샷을 재실행해 기관, 사실 버전 또는 일정을 중복 생성하지 않는다.

## 7. 공개 기준

기관 공개에 필요한 최소 조건은 다음과 같다.

1. 기관명과 주소 또는 위치 식별 근거
2. 현재 영어유치원 또는 유아 대상 영어 프로그램을 운영한다는 공식 근거
3. 공식 홈페이지, 공식 SNS, 전화번호 중 하나 이상의 확인 가능한 연락 채널
4. 근거가 연결된 검수 기록

원비, 셔틀, 급식, 후기는 공개 필수 항목이 아니다. 필수 항목이 아니어도 coverage 상태를 표시해 사용자가 확인 수준을 알 수 있어야 한다. 날짜·금액·필수 조건·기관 정체성에 충돌이 있으면 공개하지 않는다.

## 8. 빈 상태와 오류 처리

상태별 기본 문구는 섹션 이름을 포함해 생성한다.

| 내부 상태 | 사용자 문구 예시 |
| --- | --- |
| `NOT_RESEARCHED` | `원비 정보를 준비하고 있어요.` |
| `CHECKED_NOT_FOUND` | `확인한 공식 안내에서 원비 정보를 찾지 못했어요.` |
| `ACCESS_FAILED` | `기관 페이지를 불러오지 못해 원비를 확인하지 못했어요.` |
| `NEEDS_REVIEW` | `원비 내용을 확인하고 있어요.` |
| 기관이 미발표를 명시 | `기관 안내에 따르면, 아직 설명회 일정이 발표되지 않았어요.` |
| 지난 일정 | `지난 설명회예요.` |
| 신청만 마감 | `설명회 신청이 마감됐어요.` |

페이지 요청이 실패했지만 이전에 확인한 유효한 정보가 있으면 이전 값을 유지하고 `지금은 이전에 확인한 정보를 보여드리고 있어요.`를 추가할 수 있다. 이전 정보가 없으면 이 문구를 사용하지 않는다.

외부 링크가 사라졌거나 유효성 검사에 실패하면 버튼을 숨기거나 비활성 빈 버튼을 만들지 않고, 이용 가능한 다른 공식 연락 수단만 제공한다. 공개 API 장애 시에는 `정보를 불러오지 못했어요. 잠시 후 다시 시도해 주세요.`와 재시도 행동을 제공한다.

## 9. 관리자와 반입 운영

초기 MVP의 관리자 범위는 다음으로 제한한다.

- 영어유치원 기관을 `DRAFT`로 조회
- 항목별 coverage 상태 확인
- 사실 버전과 연결된 공식 근거 확인
- 기관별 공개 기준 통과 여부 확인
- 명시적으로 기관 공개

후기 자동 수집·자동 요약, 브라우저 내 대규모 편집기, 자동 공개는 초기 범위에서 제외한다. 신규 사실은 검수 전에는 현재 공개값이 될 수 없다.

## 10. 검증 계획

### 데이터베이스와 마이그레이션

- 기존 사립초 데이터가 변경되지 않는지 확인
- `MEALS` 사실 유형과 coverage·review 제약 검증
- 기관별·사실 유형별 현재 버전의 유일성 검증
- 잘못된 기관·source·snapshot 연결 거절 검증
- 롤백 후 데이터가 남지 않는지 검증

### 반입

- 25개 기관 수, 외부 키와 카테고리 확인
- 동일 스냅샷 재실행 시 중복 0건 확인
- dry run과 실제 반입의 생성·갱신 건수 비교
- 모든 현재 사실·일정의 근거 연결 확인
- 수집 시각과 검수 시각이 별도로 유지되는지 확인

### 공개 API

- `ENGLISH_KINDERGARTEN` 요청이 사립초 결과를 반환하지 않는지 회귀 검증
- `DRAFT` 기관과 미검수 사실이 공개되지 않는지 확인
- 학년도가 다른 원비가 잘못 비교·정렬되지 않는지 확인
- 설명회 신청 마감과 행사 종료 상태를 구분하는지 확인
- 공식 사실과 후기 인사이트가 서로 다른 필드로 전달되는지 확인

### UI와 UX Writing

- 목록 카드에서 금액·학년도·납부 단위가 함께 보이는지 확인
- 미발표·미발견·접근 실패·검수 필요 문구를 각각 검증
- 외부 버튼 문구와 실제 이동 목적지가 일치하는지 확인
- 모바일에서 날짜·금액·조건과 예외가 분리되지 않는지 확인
- 공식 출처, 자료 수집 시각, 내용 확인 시각을 구분하는지 확인
- 오래된 유효 정보와 최신 접근 실패가 함께 있는 회귀 사례를 검증

## 11. 단계별 출시

1. DB 마이그레이션과 유형별 검증 스키마
2. 영어유치원 전용 읽기 서비스와 관리자 검수 화면
3. 25곳 스냅샷 전체 검증과 프로덕션 dry run
4. 프로덕션 `DRAFT` 반입
5. 비교 중심 목록과 기관 상세 화면 구현
6. 공개 후보에 대한 최종 근거·문구·모바일 검수
7. Owner 승인 대상만 `PUBLISHED` 전환

DB 반입과 공개는 별도 단계다. 반입 성공만으로 공개 완료를 선언하지 않는다.

## 12. 초기 범위에서 제외하는 기능

- 브랜드–캠퍼스 계층과 브랜드 통합 페이지
- 지도 기반 탐색
- 사용자 직접 후기 작성과 별점
- 셔틀 경로 지도와 주소별 탑승 가능 판정
- 원비 총액 계산기
- PREPPY 내부 입학설명회 신청 처리
- 수집 결과의 자동 공개

## 13. UX Writing 검토

영향 범위는 영어유치원 목록, 기관 상세, 빈 상태, 일정 상태, 외부 이동 버튼과 공개 API의 표시 의미다.

- 사실·조건 보존: 원비에 학년도·납부 단위·별도 비용·변경 조건을 함께 저장하고 표시한다.
- 불확실성 보존: 조사 전, 공식 안내에서 미발견, 접근 실패, 기관 미발표, 검수 필요를 구분한다.
- 일정 의미 보존: 신청 마감, 지난 행사, 모집 마감을 서로 다른 상태로 유지한다.
- 근거 보존: 공식 출처, 자료 수집 시각, 내용 확인 시각을 분리한다.
- 후기 구분: 후기 요약을 공식 정보와 구분하고 표본·기간·출처를 표시한다.
- 행동 일치: 외부 버튼이 수행하는 이동이나 전화 행동을 버튼 이름에 명시한다.

`UX Writing: PASS` — 설계 문구와 상태 정의를 정책에 대조했다. 실제 브라우저 반응형 검사, 스크린리더 검사와 수집 데이터 회귀 검증은 구현 후 수행해야 하며 이 문서에서 통과했다고 간주하지 않는다.
