# PREPPY UX Writing 정책 v1.0

- 상태: Owner 승인 · 프로젝트 필수 기준
- 승인일: 2026-09-01
- 적용 대상: 기획, UX, 디자인, 개발, QA, 마케팅, 콘텐츠, SEO, AI/자동 생성 문구
- 적용 범위: PREPPY에서 사용자가 읽거나 행동의 근거로 삼는 모든 문구
- 운영 지침: [AGENTS.md](../AGENTS.md) · [CONTRIBUTING.md](../CONTRIBUTING.md)

**부모가 입학정보를 빠르게 이해하고, 필요한 준비를 놓치지 않도록 돕는다.**

토스가 공개한 명확함·간결함·친근함·존중·공감의 가치와, 쉬운 표현·불필요한 반복 제거·행동을 예측할 수 있는 문구 원칙을 바탕으로 했어요. 여기에 PREPPY의 특성인 **공식 근거, 입학 조건, 일정과 학년도의 정확성**을 우선 기준으로 더했어요. 참고한 공개 자료는 [토스의 8가지 라이팅 원칙들](https://toss.tech/article/21022)(2022-11-15)이에요. 토스의 최신 내부 정책을 대변하는 문서는 아니에요.

이 문서는 PREPPY의 UX Writing 단일 기준이에요. 다른 문서와 템플릿에서는 이 문서를 연결하고, 별도의 경쟁 정책을 만들지 않아요. 아래 문구 예시는 작성 방식을 설명하기 위한 것이며 특정 학교의 최신 모집정보로 사용하지 않아요.

## 1. PREPPY의 목소리

PREPPY는 **공식 안내를 꼼꼼히 읽고, 필요한 내용을 차분하게 설명해 주는 안내자**처럼 말해요.

- **정확하게:** 확인된 사실과 확인하지 못한 내용을 구분해요.
- **쉽게:** 입학 제도를 처음 접하는 보호자도 이해할 수 있게 설명해요.
- **친근하게:** 자연스러운 존댓말을 사용해요.
- **차분하게:** 입학에 대한 불안이나 경쟁심을 자극하지 않아요.
- **존중하며:** 가족 형태, 경제적 여건, 사전 지식을 단정하지 않아요.

규칙이 충돌할 때의 우선순위는 다음과 같아요.

**사실과 조건 보존 → 이해하기 쉬움 → 간결함 → 친근한 말투**

짧고 부드러운 문장을 만들기 위해 중요한 조건을 삭제하지 않아요.

## 2. 말투와 문장 규칙

### 본문은 해요체를 사용해요

| 용도               | 기본 표현                    |
| ------------------ | ---------------------------- |
| 사실 설명          | `~이에요`, `~예요`, `~해요`  |
| 가능한 선택        | `~할 수 있어요`              |
| 필요한 행동        | `~해 주세요`, `~해야 해요`   |
| 명확한 결과        | `~돼요`, `~취소돼요`         |
| 확인이 필요한 내용 | `~인지 학교에 확인해 주세요` |
| 실제 변경 가능성   | `~달라질 수 있어요`          |

제목과 항목 이름은 `지원 대상`, `준비할 서류`, `교육비`처럼 짧은 명사형을 사용해요. 모든 제목을 질문이나 해요체로 만들지는 않아요.

직접 인용하는 공식 원문, 기관 고유명, 법정 명칭은 문체를 맞추기 위해 고치지 않아요. 인용과 PREPPY의 설명을 구분해요. 개발 문서·내부 로그의 문체까지 해요체로 강제하지는 않지만, 그 안의 사용자 노출 문구와 예시는 이 정책을 따라야 해요.

### 의무·가능·금지는 바꾸지 않아요

- `제출해야 한다`를 `제출할 수 있어요`로 바꾸지 않아요.
- `취소된다`를 `취소될 수도 있어요`로 완화하지 않아요.
- `변경될 수 있다`를 `변경돼요`로 확정하지 않아요.
- `원본만 제출`에서 `원본만`을 생략하지 않아요.

예를 들어 다음 조건은 정확한 표현이에요.

> 기한까지 등록하지 않으면 입학이 취소돼요.

이 조건을 다음처럼 바꾸면 안 돼요.

> 가능하면 기한까지 등록해 주세요.

말투는 부드러워졌지만, 필수 조건이 권장사항으로 달라졌기 때문이에요.

### 한 문장에는 하나의 중심 내용을 담아요

설명이 길면 문장을 나누되, 조건과 예외가 서로 떨어져 오해를 만들지 않도록 해요.

`단`, `다만`, `제외`, `별도`, `한해`, `최대`, `최소`는 중요한 조건일 수 있으므로 무조건 줄이지 않아요.

## 3. 부모가 정보를 찾는 순서로 구성해요

한 학교의 모집 안내는 다음 질문에 답할 수 있어야 해요.

1. 어느 학년도 모집인가요?
2. 우리 아이가 지원할 수 있나요?
3. 언제까지 무엇을 해야 하나요?
4. 어떤 서류를 준비해야 하나요?
5. 비용은 얼마인가요?
6. 어떤 예외나 주의사항이 있나요?
7. 어디에서 공식 안내를 확인할 수 있나요?

### 서로 다른 질문을 한 제목에 묶지 않아요

다음 항목은 각각 구분해요.

- 지원 대상
- 지원 자격
- 모집 인원
- 준비할 서류
- 원서접수
- 추첨
- 등록
- 쌍둥이 지원
- 대기자와 결원 충원
- 교육비
- 납부 방법
- 통학
- 유의사항

`대상·인원·서류`, `접수·추첨·등록`처럼 서로 다른 내용을 한 덩어리로 표현하지 않아요. 세미콜론으로 여러 조건을 이어 붙이지 않아요. 정보가 없는 항목을 채우기 위해 빈 섹션이나 가상의 내용을 만들지 않아요.

### 중요한 값부터 보여줘요

날짜·시간·금액·인원·마감 조건을 설명 속에 숨기지 않아요.

> **11월 11일 오후 4시 30분까지 신청해 주세요.**
>
> 입학포털에서 온라인으로 신청할 수 있어요.

위 문장은 작성 방식의 예시예요. 실제 화면에서는 해당 학교의 공식 일정과 학년도를 사용해요. 맥락만으로 연도를 알 수 없다면 연도도 표시하고, 시각의 기준 시간대도 명확하게 해요.

### 공통 내용은 한 번, 서로 다른 조건은 각각 보여줘요

여러 설명회가 있다면 같은 페이지에서 날짜와 시간을 비교할 수 있게 해요.

공통 지원 대상은 한 번 안내하되, 특정 일정에만 적용되는 참석 대상·예약 기한·장소는 해당 일정 가까이에 표시해요. 공식 회차 이름은 유지할 수 있지만, `1·2·3`이라는 번호만으로 일정을 구분하게 만들지는 않아요.

## 4. 입학정보에서 반드시 보존할 내용

### 학년도와 실제 날짜를 구분해요

`2027학년도 모집`과 `2026년 원서접수`는 함께 존재할 수 있어요.

- 접수 연도로 학년도를 추측하지 않아요.
- 오래된 안내를 근거 없이 `최신 모집`이라고 부르지 않아요.
- 원문에 학년도나 날짜가 충돌하면 임의로 고치지 않아요.
- `예정`, `안`, `변경 가능`이라는 조건은 관련 일정 가까이에 남겨요.

### 비용에는 기준과 범위를 함께 표시해요

금액만 남기지 않고 다음 내용을 함께 보존해요.

- 기준 학년도
- 월·분기·연간 등 납부 단위
- 1회 납부 여부
- 별도 비용
- 환불 조건
- 다음 학년도 변경 가능성

예를 들어 다음과 같이 설명해요.

> 수업료는 2025학년도 기준 분기 2,520,000원이에요.
>
> 2026학년도에는 달라질 수 있어요. 방과후학교 비용은 별도예요.

이를 `수업료 2,520,000원`으로 줄이지 않아요.

### 접수 상태와 행사 상태를 구분해요

- 설명회 신청이 끝났다면 `설명회 신청 마감`
- 원서접수가 끝났다면 `원서접수 마감`
- 행사 날짜가 지났다는 사실만 확인된다면 `지난 일정`

신청이 마감됐다는 이유로 행사가 끝났다고 표현하지 않아요.

## 5. 모르는 내용을 정확하게 말해요

**확인하지 못한 것은 없는 것이 아니에요.**

| 실제 확인 상태                | PREPPY 표현                                                             | 사용 조건                                       |
| ----------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------- |
| 공식 일정 확인                | `모집 일정을 확인했어요.`                                               | 해당 일정의 공식 근거가 있어야 해요.            |
| 공식 예정안 확인              | `예정된 일정이에요. 변경될 수 있어요.`                                  | 공식 안내의 예정·변경 조건을 유지해요.          |
| 학교가 미발표 상태를 명시     | `학교 안내에 따르면, 아직 모집 일정이 발표되지 않았어요.`               | 단순히 찾지 못했다는 이유로 사용하지 않아요.    |
| 확인한 안내에서 발견하지 못함 | `확인한 공식 안내에서 모집 일정을 찾지 못했어요.`                       | 확인 범위를 넘어서 단정하지 않아요.             |
| 페이지 접근 실패              | `학교 페이지를 불러오지 못해 모집 일정을 확인하지 못했어요.`            | 수집 실패를 정보 부재로 바꾸지 않아요.          |
| 학년도 불명확                 | `이 안내가 어느 학년도에 해당하는지 확인이 필요해요.`                   | 학년도를 추정해서 채우지 않아요.                |
| 날짜·조건 상충                | `안내에 적힌 날짜가 서로 달라요. 정확한 마감일은 학교에 확인해 주세요.` | 충돌하는 값과 필요한 확인 행동을 함께 안내해요. |

`준비 중`, `Coming soon`, `일정 없음`을 모든 빈 상태에 공통으로 사용하지 않아요. 최신 수집에 실패했더라도 이전에 확인한 유효한 정보가 남아 있다면 그 정보를 지우거나 전체를 정보 없음 상태로 바꾸지 않아요.

## 6. 공식 출처와 확인 시점을 정직하게 안내해요

### 내부 작업 용어는 사용자 언어로 바꿔요

일반 화면에서는 `Evidence`, `VERIFIED`, `Snapshot`, `추출값` 같은 내부 용어를 사용하지 않아요.

공식 출처는 `학교 공식 안내`, `공식 모집요강`, `학교 입학 안내`처럼 내용을 예상할 수 있게 표현해요.

PREPPY의 검수를 `학교 인증`, `입학 가능 보장`으로 표현하지 않아요.

### 수집과 검수는 서로 다른 일이에요

| 사용자에게 보여줄 이름 | 의미                                    |
| ---------------------- | --------------------------------------- |
| 자료 수집              | 공식 자료를 가져온 시점                 |
| 내용 확인              | 운영자가 자료와 표시 내용을 대조한 시점 |

두 값은 내부의 Last Collected와 Last Verified에 각각 대응해요. 하나의 `최근 업데이트`로 합치거나 서로 대체하지 않아요. 수집 시각을 운영자의 검수 시각으로 복사하지 않아요.

### 편집자 설명을 없애더라도 실제 조건은 남겨요

`PDF 3쪽을 확인했어요`, `원문 표현을 보존했어요` 같은 작업 설명은 본문에서 덜어낼 수 있어요.

하지만 같은 문장에 포함된 다음 내용은 남겨야 해요.

- 원본 서류 제출 조건
- 제출 기한과 방법
- 비용과 납부자명 조건
- 대기자 유효기간
- 개인정보 동의 거부에 따른 제한
- 학교 확인이 필요한 날짜나 자격
- 다음 학년도 비용 변경 가능성

**특정 단어가 들어 있다는 이유로 문장 전체를 삭제하지 않아요.** `PDF`, `원문`, `임의로` 같은 단어를 지우는 규칙으로 실제 조건까지 삭제해서는 안 돼요. 출처의 이름을 읽기 쉽게 다듬더라도 실제 공식 링크와 원본 근거는 보존해요.

## 7. 버튼과 오류 문구는 다음 행동을 알려줘요

### 버튼은 실제로 일어나는 일을 설명해요

| 피할 표현     | 권장 표현               |
| ------------- | ----------------------- |
| 자세히 보기   | 모집요강 보기           |
| 바로가기      | 학교 입학 안내 열기     |
| 확인          | 준비할 서류 보기        |
| 지금 신청하기 | 학교 신청 페이지로 이동 |

마지막 표현은 실제 신청을 PREPPY가 처리하는 것이 아니라 외부 학교 페이지로 이동하는 경우에 사용해요.

버튼이 로그인 화면으로 이동한다면, 신청이 바로 완료되는 것처럼 표현하지 않아요. 버튼이나 링크의 접근성 이름도 실제 행동과 일치해야 해요.

### 사용할 수 없는 기능과 실행 오류를 구분해요

- 제공하지 않는 기능은 빈 버튼이나 `현재 신청할 수 없습니다` 문구로 화면을 채우지 않아요.
- 사용자가 실행한 작업이 실패했다면 오류를 숨기지 않아요.
- 오류에서는 **무엇이 안 됐는지와 다음에 할 수 있는 일**을 알려줘요.
- 원인을 모르면 네트워크나 사용자 잘못으로 단정하지 않아요.
- 실제 신청 마감이나 자격 제한은 기능 미제공과 다르므로 숨기지 않아요.

예를 들어 다음과 같이 설명해요.

> 정보를 불러오지 못했어요. 잠시 후 다시 시도해 주세요.

이전 정보가 실제로 남아 있는 경우에만 다음 안내를 덧붙여요.

> 지금은 이전에 확인한 정보를 보여드리고 있어요.

## 8. 불안을 자극하거나 과도하게 친한 척하지 않아요

다음 표현은 사용하지 않아요.

- `우리 아이의 미래가 달렸어요!`
- `지금 안 하면 늦어요!`
- `합격의 기회를 놓치지 마세요!`
- `걱정하지 마세요. 문제없어요!`
- 근거 없는 `간단한`, `완벽한`, `확실한`
- 가족을 특정하는 `엄마라면`, `아빠가 꼭`
- 불필요한 느낌표·이모지·유행어

실제 마감과 불이익은 정확하게 안내해요. 다만 가입이나 클릭을 유도하기 위한 압박으로 사용하지 않아요.

PREPPY의 공감은 과장된 응원보다 **준비할 일을 명확하게 정리하고, 불확실한 부분을 솔직하게 알려주는 것**으로 표현해요.

마케팅·광고·검색 설명에서도 같은 원칙을 적용해요. 클릭률을 높이기 위해 합격 보장, 학교 인증, 비용, 최신성, 희소성, 무료 여부를 근거 없이 주장하지 않아요. 소개 문구에서 한 약속과 실제 도착 화면의 제공 내용을 일치시켜요.

## 9. 공개 전 검수 기준

문구를 새로 쓰거나 수정할 때 다음 항목을 확인해요.

- [ ] 처음 읽는 보호자도 무엇을 뜻하는지 이해할 수 있나요?
- [ ] 소리 내어 읽었을 때 자연스러운가요?
- [ ] 중요한 날짜·금액·조건을 빠르게 찾을 수 있나요?
- [ ] 학년도와 실제 날짜, 비용 기준이 보존됐나요?
- [ ] 의무·가능·금지·예외의 의미가 달라지지 않았나요?
- [ ] 미발표·미발견·접근 실패를 구분했나요?
- [ ] 예정·변경 가능·학교 확인 필요 조건이 남아 있나요?
- [ ] 공통 문구를 줄이면서 개별 일정의 조건을 지우지 않았나요?
- [ ] 공식 출처와 수집·확인 시점을 추적할 수 있나요?
- [ ] 버튼을 누른 뒤의 동작이 문구와 일치하나요?
- [ ] 특정 단어를 제거하면서 실제 정보까지 삭제하지 않았나요?
- [ ] 모바일 화면에서도 제목과 문장 구분이 명확한가요?

사실·날짜·금액·필수 조건·불확실성에 문제가 있으면 공개를 보류해요. 문구 수정 과정에서 원본 데이터나 근거를 덮어쓰지 않아요.

## 10. 모든 직무와 작업에 적용하는 필수 운영 지침

### 작업 시작 전에 확인해요

모든 PREPPY 작업자는 기획·설계·문구 작성·구현·리뷰 전에 이 정책을 읽고 사용자 언어에 미치는 영향을 확인해야 해요. AI 에이전트와 위임받은 작업자도 같아요. 마지막에 문구만 고치는 절차로 미루지 않아요.

사용자 언어에 영향을 주지 않는 내부 작업도 검토를 생략하지 않고 `UX Writing: N/A`와 구체적인 이유를 기록해요. DB·API·스크립트 작업이라는 이유만으로 N/A라고 판단하지 않아요. 출력값이 사용자 화면·이메일·검색 설명에 전달되는지 확인해요.

### 직무별 필수 산출물을 남겨요

| 작업              | 반드시 고려할 내용                                                                     |
| ----------------- | -------------------------------------------------------------------------------------- |
| 기획·PRD          | 사용자의 질문, 핵심 메시지, 다음 행동, 정보 없음·실패·예정·상충 상태별 문구            |
| UX·디자인         | 정보 순서, 제목과 항목 분리, 실제 조건을 포함한 문구, 모바일 줄바꿈, 접근성 이름       |
| 개발              | 표시 로직의 의미 보존, 공통·개별 조건 구분, 실제 데이터 회귀 사례, 빈 상태와 오류 처리 |
| QA·리뷰           | 원문과 표시 내용의 대조, 누락·단정·시점 혼동, 링크 동작과 실제 렌더링                  |
| 마케팅·콘텐츠·SEO | 근거 있는 주장, 비용·학년도·제약 보존, 불안 조장 금지, 도착 화면과 약속 일치           |

### 완료·공개 기준으로 적용해요

사용자 노출 문구에 영향이 있는 작업은 완료 보고와 PR에 다음 내용을 남겨야 해요.

1. 영향을 받는 화면·채널·사용자 상태
2. 변경 전후 문구 또는 신규 문구와 적용 이유
3. 보존한 사실·조건·예외·불확실성과 근거
4. 검토한 오류·빈 상태·외부 이동·모바일 표시 등 해당 사례
5. 검증 근거와 결과: `UX Writing: PASS` 또는 `UX Writing: FIX_REQUIRED`

순수 내부 작업은 검토 결과가 정말 비해당인 경우에만 `UX Writing: N/A — 사유`를 사용해요. 기획안이나 문서에는 실제 수행한 문구 검토를 기록하고, 아직 하지 않은 브라우저 검사나 사용자 테스트를 통과했다고 쓰지 않아요. 코드에서 추출·필터·표시 로직을 바꾸는 경우에는 실제로 문제가 됐던 전체 문장·요강을 이용해 정보 보존 회귀를 검증해요.

위반이나 검수 누락이 있으면 해당 작업을 완료·공개 가능한 상태로 보고하지 않아요. 이 기준은 문서와 리뷰를 통한 필수 준수 규칙이며, 체크박스만으로 사실 검증이나 CI 자동 차단이 구현됐다는 뜻은 아니에요.

기존 화면을 모두 고쳤다고 간주하지 않아요. 현재 작업에서 다루는 사용자 문구와 의미에 정책을 적용하고, 범위 밖의 문제는 별도로 기록해요. 이 정책은 새 기능·전체 문구 재작성·DB 수정·수집·commit·push·배포 권한을 부여하지 않아요.

### 변경과 예외를 명시해요

기존 승인된 보안·공식 근거·검증·공개 권한 규칙을 완화하지 않아요. 정책과 요구사항이 충돌하면 영향과 선택지를 명시하고 Owner의 명시적인 결정을 받아요. 에이전트가 임의로 예외를 만들거나 검수 결과를 생략하지 않아요. 정책 변경은 이 문서에서 관리하고, Owner가 승인한 결정과 날짜를 기록해요.
